# Pages

This page covers the two page files webbundle writes for your browser router, for a developer keeping the router's pages and the server's pages the same.

## Where the page files come from

Your UI package declares its pages once, as the `[]httpserver.Page` it passes to `httpserver.SPA`. `RenderPages` and `RenderPageCorpus` turn that table and your API prefix into two files under `Src`, which you write from `go generate` and commit:

- `PagesFile`, `pages.gen.ts` by default, the page table your router imports.
- `PageCorpusFile`, `pages.corpus.gen.json` by default, the paths your router's test checks.

`Build` renders both again and fails when either file is missing or differs, with an error that says to run `go generate`. A page added on the server therefore cannot ship without the router knowing it.

Both functions refuse what `httpserver.NewPageMatcher` refuses, such as two conflicting patterns, a page at or under the API prefix, or an empty prefix. They also refuse a page named `__proto__`, because that key would set the TypeScript object's prototype instead of adding a page.

## The page table

The page table maps each page's name to its pattern, in the order of your table, and exports the API prefix:

```ts
// Code generated by webbundle. DO NOT EDIT.

export const PAGES = {
  library: "/library",
  entry: "/library/{id}",
  settings: "/settings/{part...}",
} as const;
export const API_PREFIX = "/api";
```

## The page corpus

The page corpus is a JSON array of paths with the answer `httpserver.PageMatcher` gives for each, so your router's test can check that the router answers the same. Each case is one of three shapes:

| Shape | Meaning |
| --- | --- |
| `{"path", "name", "params"}` | The path is that page, with each wildcard's decoded value |
| `{"path", "redirect"}` | The server redirects the path to `redirect`, keeping the query |
| `{"path"}` | No page answers the path |

For each pattern, the corpus holds its sample path, with each `{x}` filled with `a` and each `{x...}` with `a/b`, and these variants of it:

- the sample with a trailing slash added, or removed when it ends with one
- the sample with a leading `.` segment, with a leading `x/..` pair, and with a `%2e%2e` segment
- the sample with a repeated leading slash, and each of the sample and that path with a `?q=1` query
- each wildcard filled with `a%2Fb`, `%C3%A9` and `a%20b`

Then come `/`, `/no-such-page`, the API prefix and a path under it. A path already listed is not repeated, and a pattern gives at most 32 cases.

```json
[
  {"params": {}, "path": "/library", "name": "library"},
  {"path": "/library/"},
  {"path": "/./library", "redirect": "/library", "serverOnly": true},
  {"path": "//library?q=1", "redirect": "/library?q=1"},
  {"params": {"id": "a/b"}, "path": "/library/a%2Fb", "name": "entry"},
  {"params": {"id": ".."}, "path": "/library/%2e%2e", "name": "entry", "serverOnly": true},
  {"path": "/api/x"}
]
```

A case whose path holds a `.` or `..` segment, in any spelling such as `%2E%2e`, carries `"serverOnly": true`. A browser's URL parser removes those segments before your router reads the path, so the router's test skips them, and only the server meets them.
